日期：2026-10-17。所有运行测试均在本地隔离服完成，未操作生产服。

## 修改

`slime/SlimeChunkService.java`：同世界 UUID、同区块共享正在执行的查询和成功结果，30 秒有效期，最多 8192 项；仅缓存 UUID/坐标/结果，不长期缓存 World 或 Chunk 对象。调用者的超时/取消独立；失败移除并允许重试。原来 1024 个实际后台并发上限、15 秒查询超时和卸载排空保留。世界卸载和插件关闭清理缓存。

`visual/ChunkVisualizationService.java`：保留仍属于当前范围的显示，只移除退出范围的格子并补齐新增格子。显示实体实际锚在玩家附近，因此每移动两格区块或切换世界时重新锚定，避免保留的实体离开客户端追踪范围。配置重载清缓存并重新显示。默认半径 4、刷新间隔 5 tick 不变。

`GreenChunkPlugin.java` 注册世界卸载监听；`build.gradle` 版本升级；`SlimeChunkServiceTest.java` 增加缓存/取消隔离/容量/世界隔离/失效/失败重试验证。沿用原来的玩家、实体和区域调度，不新增执行线程、运行依赖或配置键。

## 方法和结果

同一组 8 个真实协议客户端、同一个已经加载的平坦世界。先预热路线，再测试 v5，在线卸载替换加载 v6 后测试相同脚本。计数 agent 仅在内存插入调用计数，磁盘 JAR 不变。后台计数分别放在 v5 原始实际加载入口和 v6 私有 `load`，公开查询调用仍存在，不能说所有逻辑扫描消失。

每版本两轮重复开图，每轮 8 人各开 20 次，共 320 次；两轮移动，每轮 8 人各移动 20 步，共 320 次扫描。移动沿相邻区块路线往返，使用 `teleportAsync`，每步 16 格、间隔约 1 秒。各版本另有 10 秒静止样本，静止没有后台查询或显示创建。

| 两轮合计指标 | 2.0.0-5 | 2.0.0-6 | 减少 |
| --- | ---: | ---: | ---: |
| 重复开图实际后台区块查询 | 17,280 | 108 | 99.375% |
| 移动扫描实际后台区块查询 | 25,920 | 195 | 99.248% |
| 移动时显示创建调用 | 3,072 | 1,696 | 44.792% |
| 移动时显示移除调用 | 3,072 | 1,696 | 44.792% |

开图每批 8 人，从脚本发命令到所有客户端收到地图：中位数 251.75 → 217.65 ms，缩短 **13.54%**；P95 313.22 → 263.30 ms，缩短 **15.94%**。该数据含客户端控制器约 10 ms 轮询及调度/网络等待，不是单玩家纯插件执行时间。

整个 Java 进程 CPU（一个核满载按 100%）：移动两轮旧版 16.79%/14.48%，新版 17.22%/14.04%，**没有稳定下降**。开图旧版 20.93%/8.15%，新版 10.94%/5.67%，但同一世界随时间变化，生物数量也变化，不能把整服 CPU 差异全归因于插件。没有证据支持“整服提速 99%”或客户端 FPS 提升比例，也未测出可靠的内存节省比例。新版增加了有上限的结果缓存，是用少量有界存储换取重复工作减少。

## 正确性与热更新

- 对两轮共 320 组玩家位置逐一对照：同坐标的实际 BlockDisplay 数量与旧版一致，新版确实复用部分实体 ID。另核对共 640 次地图发送。
- 新版 81 个区块各查两次，162 次结果与同一区块所属区域上的核心 `Chunk.isSlimeChunk()` 比较，0 不一致。
- 8 人同时开启地图和显示时，实际 v5 卸载 → 替换 v6 JAR → 加载；每人收到关闭地图，加载后恢复 8 个显示任务、80 个显示实体。v6 再重载同样恢复，最终离开后实体和面板会话计数归零。
- v6 面板专项：三轮卸载/加载关闭自己的地图，保留其他插件后来打开的面板；网络处理器计数 1 → 0；重载、停用/启用、断线场景通过。
- v6 热加载专项：玩家 reload、plm restart、命名空间别名、控制台前导斜杠、实际 TCP RCON reload、disable/enable、权限拒绝、仅操作权限通过；all/* 批量操作拒绝且当前显示不变。旁观客户端看不到其他玩家私有显示，卸载/关闭后没有旧显示 ID。
- 新版远距离传送到 4096 区域、相邻区块移动、切换下界、配置重载后检查客户端实体；远传和换世界移除旧 ID，相邻移动复用 ID，配置重载重新查询并重建，关闭后显示实体和任务为零。坐标传送不单独作为“多个独立 Folia 区域并发”的证明。
- 最终 `gradlew.bat clean check jar sourcesJar --init-script ../ascii-build.init.gradle --no-daemon` 退出 0；22 项测试，0 失败/错误；项目 `verifyPluginJar` 和技能独立 JAR 校验均通过。最终干净构建哈希与实际运行测试 JAR 相同。

## 玩家与管理员影响、边界

玩家操作、中文提示、查询判定和可见范围保持一致；反复开图等待在本次测试中缩短，移动时减少显示重建。客户端帧率未测，不承诺 FPS 提升。

管理员不需要新增配置。多人在相同区域反复查询时收益较大；大量玩家各自探索从未访问的区块时，缓存收益会降低。核心在运行中改变史莱姆判定规则后，`/greenchunkreload` 可立即清缓存并刷新三维显示；不执行时后续查询最多使用创建后 30 秒内的缓存。已打开的地图一直是静态快照，需要重开。

2.0.0-5 可按已验证的单插件卸载 → 等待成功 → 替换 JAR → 按文件名加载流程更新；回滚同理，保留配置。生产仍为 1.4x 或 2.0.0-3 及更早版时应停服替换，不能把新版热清理能力套到旧实例。只支持 README 列出的 PlugManX 入口，不支持任意第三方 API 强制禁用。

本次只有 8 客户端、平坦世界和指定核心，未验证数百人、生产全套插件/地形包、真实网络延迟或长时间堆占用。不能用当前比例推算整个生产服务器的 CPU/TPS/FPS。

本地原始证据位于工作区 `.codex-audit-greenchunk-20261017/perf-v6/`：`results.json`、`validated.json`、`upgrade.json`、`compare.cjs`、`validate.py`、`PerfAgent.java`、`PerfProbe.java`、`ParityProbe.java`、`hotreload-client-evidence.json`、`dialog-client-evidence.json`、`transition-evidence.json`。运行日志为审计目录的 `runtime-comparison-v5-v6.log`，采样为 `perf/samples.jsonl`。测试探针与 agent 不放入正式插件。
